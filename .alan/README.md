# Alan cloud environment

This directory holds the environment Alan builds for every session of this
repository. It contains no credentials: the Supabase and Stripe keys the app
expects are generated locally at install time.

| File | Role |
| --- | --- |
| `environment.json` | Build input: apt packages, env, install steps |
| `setup.sh` | Runs once per image build: tool binaries, `npm ci`, database, seed data |
| `start.sh` | Runs on every session boot: database, auth, REST, gateway, Next.js |
| `local-supabase/` | The local Supabase-compatible stack and its SQL |

## Why a local Supabase

The app was built against a hosted Supabase project that this environment
cannot reach, and the image builder has no Docker daemon, so the stack runs as
three native services instead of containers:

- **PostgreSQL 16** on `127.0.0.1:54322`, cluster in `~/.local/share/spotify-clone/pgdata`
- **GoTrue** (Supabase auth) on `127.0.0.1:9999`
- **PostgREST** on `127.0.0.1:54330`
- **Gateway** on `127.0.0.1:54321`, which serves `/auth/v1`, `/rest/v1` and a
  small `/storage/v1` file store so the app's `NEXT_PUBLIC_SUPABASE_URL` works
  unchanged
- **Next.js dev server** on `127.0.0.1:3000`

`local-supabase/schema.sql` mirrors `types/db.ts`. `roles.sql` creates the
`anon`, `authenticated`, `service_role` and `authenticator` roles PostgREST
expects. `seed.sql` adds three songs whose cover art and audio are generated by
`make-media.py`.

## Using it in a session

`start.sh` runs automatically at boot. Then:

- App: http://127.0.0.1:3000
- Sign up with any email and a password of at least 6 characters. Email
  confirmation is disabled (`GOTRUE_MAILER_AUTOCONFIRM`), so the session starts
  immediately and no mail server is needed.
- Logs: `~/.local/share/spotify-clone/logs/*.log`
- Generated values (Supabase URL, anon key, service key): `~/.local/share/spotify-clone/env`

Restarting one service is safe: `start.sh` skips anything already running.
`setup.sh` is idempotent too, and re-running it regenerates the schema and seed
data without touching the JWT secret.

## Limitations

- The storage shim implements public reads and uploads only, which is what the
  app uses. There are no signed URLs, policies or bucket APIs.
- Row level security is not enabled on the application tables; every local role
  can read and write. This is a development environment, not a security model.
- Stripe keys are placeholders. The billing webhook and checkout flow need real
  Stripe credentials, which this environment does not provide.
